What Rocky's body tells his brain

Started 2026-10-06 · Revision 1 (2026-10-06) — first draft for Pat's review · status: awaiting approval · follows on from Driving the treads from rocky-pi

In one paragraph

The body service on rocky-pi already answers in JSON, and Rocky's brain already reads it once a second. What it lacks is outcomes. A drive command answers "accepted" and nothing more, and the report mixes what was asked for with what was measured. This design gives every move a number and a stated ending, separates commanded from measured, and puts every sensor reading into one common shape, with empty slots ready for the sensors we have not wired in yet.

What is there today

RequestAnswer todayGap
Drive, move, pose, stop{"ok": true}No way to follow what became of it
GET /state, treadsreachable, driving, left, right, batteryThese are the speeds asked for, not anything measured, and nothing says so
GET /state, sensorsdistance_cm, touch, color, one shared age_msEach sensor has its own shape; no place for new ones; no source
The brain (rocky/body/sense.py)Reads reachable, touch, distance_cmIgnores the treads entirely

The path to the tread motors is one-way: infrared out, nothing back, and the LEGO motors have no sensors. So "the base moved" can only ever come from a separate sensor. This design makes that honest in the data.

Decisions

DecisionWhy
D1Stay with JSON over the same endpoints. GET /state remains the one report.It works and the brain already polls it.
D2Every drive move gets a number, and POST /drive returns it.The brain can follow one move from start to end.
D3Every move ends with a stated result and reason."Not driving" alone cannot tell finished from stopped from lost.
D4The tread report holds only what was commanded. Anything measured lives under senses.One place per fact; the brain never mistakes a wish for a reading.
D5Every sense has the same shape: value, source, age_ms. A value of null means "not known".Pat, 6 October: "we need to unify it with some of the sensor readings at some point. So we need to stub that in."
D6Senses we expect but have not wired are listed now, with null values.The shape is settled before the hardware arrives; filling one in later changes no interface.
D7The old top-level distance_cm, touch and color stay until the brain reads senses, then go.Nothing breaks on the day this ships.
D8The report carries "schema": 2.A reader can tell which shape it has.
D9The bridge, which runs the move, is the one that records how it ended. The body service passes that on and keeps no copy of its own.Two records of the same ending would drift apart.

The life of a move

"Finished" means the bridge sent every command and the closing stop. It does not mean the base moved. Whether it moved is a question for senses.motion, which is empty until a sensor fills it.

The new shape

POST /drive  {"left": 4, "right": 4, "ms": 1500}
→ 200 {"ok": true, "move": {"id": 17}}

GET /state
{
  "schema": 2,
  "reachable": true,                       // the arm's controller, as today
  "controller": "nxt",
  "joints": { "pan": {"deg": 12.0, "state": "moving"} },

  "drive": {
    "kind": "badge", "target": "tread", "reachable": true,
    "commanded": { "left": 4.0, "right": 4.0, "ms_left": 800 },
    "last_move": {
      "id": 17,
      "asked":  { "left": 4.0, "right": 4.0, "ms": 1500 },
      "result": "running",                 // running | finished | replaced | stopped | lost | refused
      "ended_by": null,                    // time | new_move | stop | unreachable | <refusal reason>
      "age_ms": 700                        // since it started, or since it ended
    }
  },

  "senses": {
    "distance_cm": { "value": 42,            "source": "nxt.ultrasonic", "age_ms": 180 },
    "touch":       { "value": [false, true], "source": "nxt.touch",      "age_ms": 180 },
    "color":       { "value": "red",         "source": "nxt.color",      "age_ms": 180 },
    "tread_battery_pct": { "value": 100,     "source": "badge.tread",    "age_ms": 250 },

    "motion":      { "value": null, "source": null, "age_ms": null },   // still | moving | turning
    "heading_deg": { "value": null, "source": null, "age_ms": null },
    "tilt_deg":    { "value": null, "source": null, "age_ms": null },
    "bumped":      { "value": null, "source": null, "age_ms": null }
  },

  "distance_cm": 42, "touch": [false, true], "color": "red", "age_ms": 180   // old keys, kept for now (D7)
}

Rules a reader can rely on

  • A sense is always an object with value, source and age_ms. value: null means not known; never guess from it.
  • New senses may appear at any time. A reader ignores names it does not know.
  • drive.commanded is zero whenever no move is running.
  • last_move is null until the first move after the service starts. Move numbers count up from 1 and start again when the bridge restarts; age_ms tells an old move from a new one.
  • With no [drive] section, drive is null, as today.

Where each piece lives

Testing

  • Bridge, against a pretend badge: a move that runs out ends finished/time; one replaced ends replaced/new_move and the new one has the next number; one cancelled ends stopped/stop; a badge that drops ends lost/unreachable; a stop with nothing running changes nothing.
  • Body service, against a pretend bridge: the number comes back from POST /drive; /state has the new shape with and without treads, with the arm unreachable, and with the bridge down; every sense has the three fields; the empty slots are present and null; old keys still match.
  • Brain: BodySense reacts to touch and nearness from senses exactly as before.
  • On the real base, with Pat: one move run to its end, one stopped, one replaced, and the badge switched off mid-move, checking each reported ending.

Open points

  • A badge with its own Drive app open still ignores commands silently, so such a move would be reported finished. Fixing that needs a status flag from the firmware; when it exists the ending becomes refused.
  • The arm's poses deserve the same treatment (a number and an ending per pose). Left out here to keep this small.
  • /state asks the bridge each time, so a hung bridge can slow the whole report by up to two seconds. Worth caching the tread part if it bites.
  • Battery reads 0 on the face badge. It will show as 0, not null, until the firmware reports it properly.
