Emotion Channel

A reusable way for a skill-enabled AI to inject emotions onto a device — first adopter: the Temporal badge robot face.
Started 2026-10-05 · Revision 5 (2026-10-05) — added voice (BT speaker + mic) as a host-side extension · status: ready for spec review

In one line

An AI sends a small message — mood + strength + duration — the device applies it to the robot face at once (overriding the idle liveliness), and when the duration runs out the face goes back to being lively on its own. The parts are built to be transport-agnostic and dropped into the shared code library so other projects can adopt them.

The message

{
  "mood":      "happy",   // one of: neutral happy tired sad angry
                          //         surprised curious scared
  "intensity": 0.8,       // 0.0–1.0  how strong the expression reads
  "ttl_ms":    20000,     // how long to hold it; 0 = until replaced/cleared
  "source":    "assistant" // optional, for logging/attribution
}

Intensity maps onto the face's existing tween amount (lid depth, eye-size pop); duration drives the override timer. Nothing here is badge-specific — another device could map the same message onto LEDs, a servo, or a screen.

The shared core (same for every transport)

Only the middle box — transport — changes between the options below. The library pieces are: the message schema, the device consumer (receives a message, drives the face, runs the expire timer), and a small client the AI uses to send one.

Transport options

Columns that matter: does the badge need WiFi, is there a cloud dependency, where can the AI run, and does it keep your "endpoint with an API key" model. Bluetooth hops are proximity-based (~10 m line of sight); WiFi hops need the badge connected to a network.

A · WiFi cloud relay + poll WiFi

+ Reaches the badge from anywhere on the internet.   − Needs the badge on WiFi, an always-on cloud service, and adds poll latency. WiFi is the pathway you'd rather avoid.

B · WiFi local relay + poll WiFi

Same shape as A, but the relay runs on this Mac (.test via Caddy). + No cloud; stays local.   − Still needs the badge on WiFi, and a remote AI can't reach it — only agents on your LAN.

C · Badge hosts an HTTP server WiFi

The badge serves the endpoint itself; the AI POSTs to the badge's IP. + No middle service.   − The AI must be on the same network and know the badge's IP, and it puts an inbound server (new attack surface) on the ESP32. Fragile for a badge that roams.

D · BLE bridge — small local "emotion API" relays over Bluetooth Bluetooth recommended

The badge advertises a small BLE Emotion GATT service. A tiny local bridge on the Mac exposes the API-key HTTP endpoint the AI expects, and relays each message to the badge over Bluetooth.

+ No WiFi on the badge; proximity-based and low latency; keeps your "endpoint with an API key" model; the AI can be any HTTP caller (even remote, if the bridge is reachable); the bridge + GATT service + schema are a clean reusable kit.   − One extra local process (the bridge) must be running near the badge.

E · BLE direct — the skill talks straight to the badge Bluetooth

The skill itself speaks Bluetooth (via bleak) and writes the characteristic directly — no HTTP service at all. + Leanest; fewest moving parts.   − Only works when the AI runs on a machine with Bluetooth in range; no HTTP "API key" endpoint (auth becomes a GATT shared-secret/bonding), which drifts from your original "little API service" framing.

Recommendation

Option D — BLE bridge. It satisfies everything you asked for: Bluetooth on the last hop (no WiFi on the badge), a real endpoint with an API key for the AI to call, and a clean modular kit for the library. It degrades gracefully too — the same badge GATT service also supports Option E (a local skill writing directly) with no firmware change, so "direct" stays available as a lighter path for local use.

Infinite-duration messages give you the latch-until-cleared behaviour you weren't sure about, as a special case of the same override model — no separate mode needed.

Does the agent get feedback?

In the one-way sketch earlier, no — the agent would be injecting blind. It shouldn't be, and Bluetooth makes the fix cheap: GATT is two-way, so the same service that accepts a write can answer it and expose readable state, with no second transport. That's a further point for Option D.

LevelHowWhat the agent learns

Events (optional, later)GATT notify → bridge streams/queues themPushed moments: override expired, a button was pressed, a boop happened.
GET /state  →
{
  "override":   { "mood": "happy", "intensity": 0.8, "ms_left": 12400 },  // or null
  "autonomous": "neutral",     // what the idle loop is showing when no override
  "face_on_screen": true,      // is the robot face even the active screen?
  "battery_pct": 76
}

The robot face is one screen among many. If the user has navigated away, an injected emotion has nowhere to show — so face_on_screen is part of the readback, and the bridge reports "accepted, but not currently visible" rather than letting the agent assume it worked.

What lands in the library

Transport-independent

  • Emotion schema — the message + validation (one source of truth, shared by device and client).
  • Device consumer — takes a message, drives a face/output, runs the override+expire timer. The badge's RobotFaceScreen becomes its first adopter.
  • Client — build one message, send it.

BLE-specific (Option D)

  • Badge GATT service — one "emotion" characteristic + auth, in the existing ble/ module.
  • Bridge — tiny local service: API-key HTTP in, BLE write out.
  • Claude skill — thin wrapper so a skill-enabled AI injects an emotion in one call.

Decision

Option D — BLE bridge — is the primary build, chosen for modularity: the device, the relay, and the skill stay independent, swappable pieces. Option E (direct) is supported by the same code, not a second build — both write the identical badge GATT service. The way that falls out:

  • One reusable emotion client with two interchangeable backends — a BLE backend (speaks GATT straight to the badge = E) and an HTTP backend (speaks to the bridge = D).
  • The bridge is itself just a caller of the BLE backend, wrapped in an API-key HTTP endpoint.
  • So a skill on a Bluetooth-equipped host can skip the bridge entirely; a skill elsewhere goes through it. Same schema, same device, same client library.

Detailed design

Badge — BLE GATT service (NimBLE peripheral)

A small custom GATT service added to the existing ble/ module. Characteristics:

CharacteristicAccessCarries
emotionWrite (with response)One emotion frame. Write-with-response is the delivery ack.
stateReadCurrent status struct (see readback shape above).
events (phase 2)NotifyPushed moments: override expired, button pressed, boop.

Compact binary frame (BLE-MTU friendly, ~6 bytes):

byte 0   mood       (0..7: neutral happy tired sad angry surprised curious scared)
byte 1   intensity  (0..255 → 0.0–1.0)
byte 2-3 ttl        (uint16, 100 ms units; 0 = until replaced/cleared)
byte 4   source     (small id for attribution/logging)
+ auth tag          (shared-secret token; exact scheme fixed in the plan)

Badge — how the face consumes it

  • A shared EmotionOverride object is set from the emotion write callback: { active, mood, intensity, setAtMs, ttlMs }.
  • RobotFaceScreen checks it each frame: active & unexpired → drive the mood and intensity from the override instead of the autonomous picker; expired → clear and resume the lively loop. This is the whole of "override, then expire."
  • The state read is composed from EmotionOverride + the GUI's current screen id (face_on_screen) + battery. Writes are accepted even when the face isn't the active screen; the readback reports face_on_screen:false so the agent isn't misled. v1 does not auto-switch to the face — too intrusive.

Bridge — "emotion API" (any BLE host — Mac, Raspberry Pi, Linux — Python + bleak)

EndpointDoes
POST /emotion
Authorization: Bearer <key>		Validate key → encode frame → BLE write-with-response to the badge → return { ok, applied, state }.
GET /stateRead the badge state characteristic → return it as JSON.

All settings are passed in, never baked into shared code: the API key, the badge BLE address/name, the shared secret, and the bind port (registered via the local-dev-hosting recipe, reachable at a .test host). The reusable client and bridge take these as arguments/env with defaults.

Skill — the AI's one call

A thin Claude skill over the client: inject_emotion(mood, intensity, duration) and get_face_state(). It selects the HTTP backend (bridge) or BLE backend (direct) from config, so the same skill serves D and E.

Intermediate hosts (Raspberry Pi & friends)

Because the bridge is host-agnostic Python + bleak (macOS CoreBluetooth or Linux BlueZ), the same bridge runs on a Raspberry Pi unchanged. That makes the Pi the piece that carries the network, so the badge never has to:

  • Pi as a fixed gateway. A Pi near a table or booth is the always-on networked endpoint; a remote AI (cloud, laptop, this Mac) calls it over the network, and it relays to nearby badges over Bluetooth. Network reach, badge stays offline.
  • One Pi, many badges. The bridge API takes a target badge (BLE address/name), so a single Pi addresses a cluster. Badge addresses live in the Pi's config, never in the code.
  • Tiers compose. Each hop is a backend we already have: cloud relay → Pi gateway → badge, or a skill running on the Pi talking straight to badges (that's Option E, just hosted on the Pi). Same schema and client throughout.
  • Self-contained unit. The Pi can also run the agent/skill itself — a table-top box that needs only power and proximity.

Impact on the build: the bridge must be multi-badge from the start (a target parameter + a per-host config of badge addresses). Nothing about the badge firmware changes — it's the same GATT service whether the writer is a Mac, a Pi gateway, or a direct skill.

Extension: voice — Bluetooth speaker + microphone (not v1)

A natural next capability on the same gateway: give the robot ears and a voice. Key constraint: the badge's ESP32-S3 is Bluetooth LE only — no Bluetooth Classic, and consumer speakers/mics use Classic (A2DP / HFP). So the speaker and microphone pair with the host (Mac or Pi), not the badge. That keeps audio and the heavy compute on the capable host and leaves the badge a cheap BLE expression device.

  • Composition. The agent listens (mic → speech-to-text), thinks, then speaks (text-to-speech → speaker) and drives the face in sync — the LED-matrix mouth can animate to speech amplitude/visemes for lip-sync, and the mood rides the emotion channel we're building now.
  • Why it's a sibling, not v1. It's a larger capability (audio I/O, STT/TTS, turn-taking) that only shares the gateway host. Keeping it separate lets the emotion channel ship first; this gets its own spec when we're ready.
  • What v1 should leave room for. Two small hooks: a speaking state the agent can raise so the mouth lip-syncs, and the phase-2 events notify (e.g. "heard a wake word") — both already fit the schema and GATT service, so no rework later.

What lands in the library (revised)

Reusable, project-independent

  • Wire-format + schema — the one source of truth for the frame and the /state shape.
  • C++ EmotionConsumer — device side: apply an override, run the expire timer, report state. The badge is its first adopter.
  • Python emotion client — two backends (BLE / HTTP), settings as arguments.
  • Bridge — API-key HTTP wrapper around the BLE backend.

Badge-specific glue (stays in this repo)

  • The NimBLE GATT service wiring in ble/.
  • RobotFaceScreen reading the EmotionConsumer.
  • The face_on_screen hook into GUIManager.

Risks & impact

  • BLE is currently compiled out. The firmware excludes the ble/ folder from the build and gates it behind an unset BADGE_ENABLE_BLE_PROXIMITY flag, deliberately, to keep the offline firmware small. This feature re-enables a minimal NimBLE GATT peripheral (not the proximity scanner) behind its own flag — and the flash/RAM cost must be measured against the current ~2.6 MB image and the OTA-frozen 16 MB partition layout before we commit.
  • Auth. The bridge holds the AI's API key; the badge link needs its own protection (NimBLE bonding and/or a shared-secret tag in the frame). Exact scheme is settled in the implementation plan, not hand-waved.
  • One screen among many. Handled by face_on_screen in the readback; not a silent failure.
